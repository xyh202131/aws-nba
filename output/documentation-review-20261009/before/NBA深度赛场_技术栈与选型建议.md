# NBA 深度赛场：技术栈与选型建议

> 版本：1.0 · 整理日期：2026-09-30 · 用途：竞赛首版选型与开发分工
> 状态：方案建议，尚未在参赛账号和正式比赛素材上完成实测。

**推荐路线：多模态大模型调用 API，检测与 OCR 使用现成模型权重，数据对齐、流程编排、事实校验和展示由项目自行实现。**

本方案围绕“把一个进攻回合讲清楚”设计：先识别发生了什么，再找到对应的官方数据，最后用清晰的标注和解说呈现。模型、部署方式和训练需求分别选择，避免将“使用 AI”直接等同于“自行训练模型”。

## 1. 选型前提与技术边界

根据现有培训纪要，调试素材为两段普通转播画面的进攻视频，合计约 48 秒；考试视频发布后约有两小时处理与调优时间。纪要明确要求 GitHub 私有仓库、CloudFront URL、AWS CDK 和指定 AWS Agent 服务，并允许使用外部模型 API。【S0】

因此，首版优先保证完整处理流程、内容准确性和交付可靠性。48 秒素材可以用于调试，但不足以支持可靠的模型训练或泛化结论。

| 选择 | 含义 | 首版定位 |
| --- | --- | --- |
| 调用模型 API | 由服务方运行模型，项目通过接口发送输入并获取结果 | 多模态理解、解说生成的默认方案 |
| 自部署现成模型 | 在自己的计算资源上加载已有权重进行推理 | 检测、OCR 优先；大模型作为备选 |
| 监督微调／LoRA | 使用标注数据调整已有模型参数 | 基础方案暴露稳定缺陷后再评估 |
| 从头训练／强化学习 | 训练基础模型或基于奖励学习决策策略 | 当前首版不安排，后续按数据条件立项 |

**自部署与训练是独立决策。** 加载一个开源模型进行推理不需要重新训练；Agent 部署到 AWS，也可以继续调用托管模型 API。

**已知边界：** 当前没有官方数据样例、正式评分细则、确认的 GPU 资源或完整模型 ID。下文列出的模型和工具是候选方案，不是已确认可用的参赛资源清单。赛事年份、区域与截止时间仍以正式通知为准。

## 2. AI、视觉与数据技术栈

| 模块 | 推荐技术或候选 | 运行方式 | 具体建议 |
| --- | --- | --- | --- |
| 多模态视频理解 | 主办方已开通、支持视频或多图输入的模型；Nova Pro 可作候选【S1】 | 优先 API | 识别回合过程和候选事件。按片段处理，保存输入时间戳与结果，避免重复分析同一内容。 |
| 球员检测与跟踪 | YOLO 预训练检测器 + BoT-SORT【S3】 | 现成权重推理 | 先验证球员定位和跟踪。BoT-SORT 支持相机运动补偿，可作为移动转播镜头的起点。 |
| 比分、时钟与号码识别 | PaddleOCR 的 PP-OCR 系列【S4】 | 现成权重推理 | 先裁剪记分牌等目标区域再识别。球衣号码只作为身份辅助，模糊或遮挡时保留未知。 |
| 时序事件识别 | 多模态模型 + 时间戳 + Python 校验 | API + 自研 | 优先支持传球、突破、投篮等少量事件；输出事件类别、开始／结束时间、参与者和画面依据。 |
| 官方数据对齐 | JSON／结构化表格 + 精确查询 | 自研代码 | 按官方数据实际提供的比赛、球员或事件标识匹配。保留数据来源，不让模型生成缺失指标。 |
| 知识检索与 RAG | 战术说明文档 + 检索模块 | 先简单检索 | 数值走精确查询，术语与战术说明走文档检索。知识规模扩大后再考虑 Embedding API 与向量索引。 |
| 战术解释与解说 | 大模型 + 提示模板 + 事实校验 | API + 自研 | 将已确认的事件、轨迹与数据组织为解说。明确画面观察与战术推断，不断言球员的真实意图。 |

有四个边界需要在实现中保留：

- **跟踪 ID 不等于球员身份。** 将轨迹关联到真实姓名，还需要号码、名单和上下文；镜头切换后要重新核对。
- **通用检测器的篮球识别能力需要实测。** 小目标、运动模糊和遮挡可能导致漏检。发现问题后，先调整输入与采样，再评估专项标注和微调。
- **像素距离不能直接当作球场距离。** 若展示米制距离、跑速或真实球场轨迹，需要额外的球场标定与透视处理；首版可仅显示画面内的示意标注。
- **官方指标与模型估计分开。** 预期命中率、球员引力等仅展示来源可追溯且与当前事件对应的数据；缺失时不补造精确数值。

建议保留“视频时间、比赛时钟、事件标识、球员标识、证据帧、数据来源”之间的映射。普通转播视频含回放和切镜，视频时间与比赛时钟不能默认一一对应。

## 3. 应用、视频与云端技术栈

| 模块 | 推荐技术或候选 | 实现方式 | 具体建议 |
| --- | --- | --- | --- |
| 视频预处理 | FFmpeg + OpenCV | 自研代码 | 完成切片、抽帧、裁剪和时间戳记录。事件附近可增加采样密度，避免低频抽帧漏掉快速动作。 |
| Agent 编排 | Python 工具调用 + 明确任务流程 | 自研并部署 | 用单个 Agent 配合分析、查询、校验和渲染工具。部署到主办方指定 AWS Agent 服务，具体产品名待核。 |
| 标注与成片 | OpenCV + FFmpeg【S5】 | 自研代码 | 绘制箭头、轨迹、数据卡和字幕，按统一时间轴合成；首版不需要训练视频生成模型。 |
| 交互页面 | React + TypeScript + HTML5 Video + SVG／Canvas | 自研前端 | 提供事件跳转、标注开关和数据解释。页面叠加与导出成片共用一份标注数据，减少结果不一致。 |
| 语音解说 | 云端 TTS | API，可选 | 先确认解说文本，再合成语音并处理音画同步。字幕与画面可用后，再增加声音。 |
| 云端交付 | AWS CDK + S3 + CloudFront + 视频处理工作进程 | 托管服务 + 自研 | CDK、CloudFront 对应纪要要求；S3 与工作进程是本方案建议。耗时视频处理独立执行，Agent 负责调度。 |
| 质量评估 | 核对样本 + Python 检查脚本 | 自研 | 检查事件时间、身份匹配、指标来源、画面遮挡、处理时长和运行失败，作为是否升级模型的依据。 |

建议采用以下处理顺序：

> 视频输入 → 预处理与关键事件定位 → 跟踪／OCR／官方数据对齐 → 事实校验 → 战术解读与标注生成 → 网页播放和视频输出

各模块的职责保持明确：多模态模型提供语义分析，检测与跟踪模块提供位置线索，数据查询模块提供数值依据，渲染模块负责呈现。

工程实现建议：

- 用视频标识和处理配置保存中间结果，修改字幕样式时复用已完成的分析，避免重复调用模型。
- 对模型返回结果做字段、时间范围和引用检查；不能仅因模型返回了 JSON，就视为内容正确。
- 页面显示真实任务状态，失败时支持定位与重试，避免将处理失败显示成“没有事件”。
- 不确定的身份或战术应减少展示或明确标注，避免以错误内容换取画面丰富度。
- 调用凭据保留在服务端并使用适当的凭据管理方式，前端和仓库中不包含密钥。

## 4. 多模态模型与训练路线的选择

| 路线 | 候选与主要代价 | 采用条件与建议 |
| --- | --- | --- |
| 调用多模态 API | 主办方已开通的模型；支持图像、视频输入的 Nova Pro 是可验证候选【S1】 | 默认选择。先验证账号权限、指定区域、输入格式、延迟与实际分析质量，再接入流程。 |
| 自部署现成模型 | Qwen3-VL-4B／8B 等；可使用 Transformers 或 vLLM 推理【S2】 | 有可用 GPU 和维护能力，且 API 在质量、额度或可用性上存在明确问题时采用。先加载原始权重，不同步开展微调。 |
| 监督微调／LoRA | 在开源模型上微调篮球事件或解说任务；需要标注、训练与独立验证 | 基础模型在同类场景中反复出错，且已有足够标注样本时评估。用独立视频证明改进，不能只看调试视频。 |
| 从头训练 | 自行训练检测器、视频模型或多模态基础模型 | 当前素材与周期不支持将其作为默认路线。若开展专项研究，需要单独确定数据、算力和验证预算。 |

“千问 235B”不是足够完整的模型标识，不能仅凭参数规模判断是否支持视频。选型时必须确认完整模型 ID、输入模态和实际接口；多图输入也应保留帧顺序与时间信息。

自部署的显存和速度受模型规模、精度／量化方式、帧数、分辨率、上下文长度及并发量共同影响。当前未确认硬件，不承诺固定显存需求或处理时长；应先用真实样例做小规模推理验证。【S2】

建议用同一批保留样例比较候选方案：

- 关键事件是否识别正确，发生时间是否足够准确。
- 球员身份和官方指标是否有证据，是否出现编造内容。
- 相同输入是否稳定产生可校验的结构化结果。
- 完整处理时间、调用费用或资源消耗是否能满足交付窗口。

**强化学习的定位：后续研究，不进入首版关键路径。**

若优化“何时展示哪个指标”，可在积累观众反馈后研究展示策略，奖励应同时考虑理解效果、准确性和遮挡程度。若学习传球、投篮等战术决策，则需要模拟环境或充足的离线状态、动作和结果轨迹，并定义可评估的奖励。当前两段短视频尚不能提供这些条件。

遇到识别问题时，建议先检查数据对齐、采样、提示词和规则，再更换模型；只有上述调整仍无法解决的稳定缺陷，才进入专项训练评估。

## 5. 实施顺序、验收与待核事项

| 阶段 | 建议交付 | 完成判断 |
| --- | --- | --- |
| 首版必做 | 视频输入、多模态分析、官方数据查询、简洁标注、可访问页面、合规部署 | 一段未用于调试的视频能够完成处理，重要结论能追溯到画面或数据。 |
| 按效果增强 | 跟随标注、OCR、战术细节、语音、成片导出 | 新功能改善理解效果，且没有明显增加错标、遮挡和处理失败。成片是否为强制交付需按正式规则确认。 |
| 条件成熟再做 | 大模型自部署、专项微调、强化学习 | 有明确问题、可用数据、资源预算与独立验证方案，并证明相对基础方案的收益。 |

建议的交付验收项：

- 正式作品 URL 可打开、视频可播放，事件跳转和标注开关正常。
- 关键事件时间与原视频一致，球员身份不确定时有明确处理。
- 每个官方数值均能追溯来源，并确认属于当前球员或事件。
- 标注与解说不遮挡主要动作，导出结果与页面表达一致。
- 处理耗时、错误情况及重试过程有记录；保留一次完整演示结果。
- 仓库绑定、私有状态、CDK 部署及作品 URL 提交分别完成核对。

落地前需向正式指南或主办方确认：

1. AWS Agent 服务的准确产品名称、区域和允许使用的部署方式。
2. 完整模型 ID、视频／图像支持情况、额度、调用限制与 GPU 资源。
3. 官方数据格式、时间粒度、事件标识及其与视频的对应关系。
4. 人工修正、预处理、缓存结果与赛前代码的允许范围。
5. 视频格式、交互要求、提交截止时间、年份及评分细项。
